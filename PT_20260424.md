## 2. Executive Summary

**Overall Risk Rating: CRITICAL**

The application contains numerous high-severity and critical vulnerabilities spanning nearly every category of the OWASP Top 10. The most impactful findings include:

### Key Themes
1. **Injection flaws are pervasive** — SQL injection, NoSQL injection, and code injection (RCE) are present across multiple routes.
2. **Broken authentication and authorization** — Hard-coded private keys, weak hashing (MD5), bypassable CSRF protection, broken access controls on baskets and user data.
3. **Sensitive data exposure** — Private RSA key embedded in source code, encryption keys served via HTTP, configuration data leaked via API.
4. **Server-Side Request Forgery (SSRF)** — Profile image URL upload fetches arbitrary URLs.
5. **XML External Entity (XXE) and YAML deserialization** — File upload routes process XML/YAML without proper restrictions.
6. **Remote Code Execution (RCE)** — B2B order API evaluates user-supplied expressions; XML/YAML parsers allow DoS.
7. **Path Traversal** — Null byte injection bypasses file type restrictions; zip slip in file uploads.

### Most Critical Findings
- SQL Injection in login and product search (CVSS 9.8)
- Hardcoded RSA private key enabling JWT forgery (CVSS 9.8)
- Remote Code Execution via B2B order endpoint (CVSS 9.8)
- XXE injection via file upload (CVSS 9.1)
- SSRF via profile image URL upload (CVSS 8.6)

### Immediate Priorities
1. Remove hardcoded RSA private key from source code
2. Parameterize all SQL and NoSQL queries
3. Remove or sandbox code evaluation endpoints
4. Disable XML external entity processing
5. Implement proper input validation and output encoding across all routes

## 3. Application Overview

### Architecture Summary
- **Backend:** Node.js + Express.js (TypeScript), Sequelize ORM (SQLite), MarsDB (MongoDB-like in-memory), REST API
- **Frontend:** Angular SPA served as static files
- **Authentication:** JWT (RS256) with tokens stored in cookies and Authorization header
- **Template Engines:** Handlebars (hbs) and Pug for server-rendered pages

### Key Components
| Component | Location | Purpose |
|---|---|---|
| Express Server | `server.ts` | Main application setup, routing, middleware |
| Authentication | `lib/insecurity.ts` | JWT signing/verification, password hashing, auth middleware |
| Routes | `routes/*.ts` | ~65 route handlers for REST API, file serving, auth |
| Models | `models/*.ts` | Sequelize models for SQLite database |
| Data Layer | `data/mongodb.ts`, `data/datacache.ts` | MongoDB collections, in-memory caches |
| Config | `config/*.yml` | Application configuration including OAuth, secrets |

### Authentication and Authorization Model
- JWT tokens signed with RS256 using a hardcoded RSA private key
- `express-jwt` middleware for protected routes
- Role-based access: `customer`, `deluxe`, `accounting`, `admin`
- 2FA via TOTP (optional per-user)
- Password hashing: **MD5** (no salt)

### Sensitive Assets / Data Handled
- User credentials (email, password hashes)
- Payment card information
- Personal addresses
- Order history
- Security question answers (HMAC-SHA256)
- JWT tokens, TOTP secrets
- Wallet balances

### Attack Surface Summary
| Surface | Entry Points |
|---|---|
| REST API | `/rest/*`, `/api/*`, `/b2b/*` (~40+ endpoints) |
| File Upload | `/file-upload`, `/profile/image/file`, `/profile/image/url`, `/rest/memories` |
| File Serving | `/ftp/*`, `/encryptionkeys/*`, `/support/logs/*` |
| Authentication | `/rest/user/login`, `/rest/user/reset-password`, `/rest/user/change-password` |
| Redirects | `/redirect?to=` |
| Data Erasure | `/dataerasure` |
| Chatbot | `/rest/chatbot/*` |
| Metrics | `/metrics` (Prometheus) |
| Swagger | `/api-docs` |

### Trust Boundaries
1. **Unauthenticated → Authenticated**: JWT verification via `express-jwt`
2. **Customer → Admin/Accounting**: Role checks in middleware
3. **Server → External**: Profile image URL fetching (SSRF surface)
4. **User Input → Database**: SQL/NoSQL queries
5. **User Input → File System**: File uploads, path resolution
6. **User Input → Code Execution**: B2B order processing, XML/YAML parsing

## 5. Detailed Findings

### [PT-001] SQL Injection in Login

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-89 (SQL Injection)
- **OWASP Category:** A03:2021 – Injection
- **Affected Files/Locations:** `routes/login.ts`, line 34
- **Description:** The login function constructs a raw SQL query by directly interpolating user-supplied `email` into the query string without parameterization.
- **Technical Details:** The query `SELECT * FROM Users WHERE email = '${req.body.email || ''}' AND password = '${security.hash(req.body.password || '')}' AND deletedAt IS NULL` is vulnerable. The `email` parameter is not sanitized or parameterized.
- **Evidence from Code:**
  ```typescript
  // routes/login.ts:34
  models.sequelize.query(`SELECT * FROM Users WHERE email = '${req.body.email || ''}' AND password = '${security.hash(req.body.password || '')}' AND deletedAt IS NULL`, { model: UserModel, plain: true })
  ```
- **High-Level Abuse Scenario:** An attacker could supply a crafted email value such as `' OR 1=1--` to bypass authentication entirely and log in as any user (e.g., the admin).
- **Preconditions:** None — unauthenticated endpoint.
- **Impact:** Full authentication bypass; access to any user account including admin; potential data exfiltration.
- **Likelihood:** Very High
- **Remediation:** Use Sequelize parameterized queries or the ORM `findOne` method with `where` clauses. Never concatenate user input into SQL strings.
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed by source code inspection. The `vuln-code-snippet` markers confirm this is intentional for the CTF.

### [PT-002] SQL Injection in Product Search

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-89 (SQL Injection)
- **OWASP Category:** A03:2021 – Injection
- **Affected Files/Locations:** `routes/search.ts`, line 23
- **Description:** The product search endpoint directly interpolates the `q` query parameter into a raw SQL query.
- **Technical Details:** While there is a 200-character length limit on the criteria, this is insufficient to prevent UNION-based SQL injection.
- **Evidence from Code:**
  ```typescript
  // routes/search.ts:23
  models.sequelize.query(`SELECT * FROM Products WHERE ((name LIKE '%${criteria}%' OR description LIKE '%${criteria}%') AND deletedAt IS NULL) ORDER BY name`)
  ```
- **High-Level Abuse Scenario:** An attacker could perform a UNION SELECT to extract all user credentials (emails and password hashes) from the Users table.
- **Preconditions:** None — unauthenticated endpoint.
- **Impact:** Full database read access; credential theft; schema enumeration.
- **Likelihood:** Very High
- **Remediation:** Use parameterized queries with bind variables.
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed. Code comment references `unionSqlInjectionChallenge`.

### [PT-003] Hardcoded RSA Private Key in Source Code

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-798 (Use of Hard-coded Credentials)
- **OWASP Category:** A02:2021 – Cryptographic Failures
- **Affected Files/Locations:** `lib/insecurity.ts`, line 23
- **Description:** The RSA private key used for JWT signing is hardcoded directly in the source code as a string constant. The corresponding public key is also served via `/encryptionkeys/jwt.pub`.
- **Technical Details:** The private key `-----BEGIN RSA PRIVATE KEY-----\r\nMIICXAIBAAKBgQDNwqLEe9wg...` is a 1024-bit RSA key embedded in the code. Any attacker with access to the source code (or who can infer/crack the weak key) can forge arbitrary JWT tokens.
- **Evidence from Code:**
  ```typescript
  // lib/insecurity.ts:23
  const privateKey = '-----BEGIN RSA PRIVATE KEY-----\r\nMIICXAIBAAKBgQDNwqLEe9wg...'
  ```
- **High-Level Abuse Scenario:** An attacker can sign arbitrary JWTs to impersonate any user, including admin, by crafting tokens with the stolen private key.
- **Preconditions:** Access to the source code repository (publicly available on GitHub).
- **Impact:** Complete authentication bypass; privilege escalation to admin; full application compromise.
- **Likelihood:** Very High (source is public)
- **Remediation:** Store private keys in secure key management systems (e.g., AWS KMS, HashiCorp Vault). Use environment variables at minimum. Rotate the key immediately.
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed. Key is a static string in the source file.

### [PT-004] Remote Code Execution via B2B Order Endpoint

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H)
- **CWE:** CWE-94 (Improper Control of Generation of Code)
- **OWASP Category:** A03:2021 – Injection
- **Affected Files/Locations:** `routes/b2bOrder.ts`, lines 21-23
- **Description:** The B2B order endpoint uses `vm.runInContext` to evaluate user-supplied `orderLinesData` through the `notevil` sandbox, which has known bypass techniques.
- **Technical Details:** The `notevil` library (`safeEval`) is used inside a `vm` context with a 2-second timeout. While the `vm` module provides some isolation, it is not a security boundary and can be escaped. The `notevil` library itself has known vulnerabilities.
- **Evidence from Code:**
  ```typescript
  // routes/b2bOrder.ts:21-23
  const sandbox = { safeEval, orderLinesData }
  vm.createContext(sandbox)
  vm.runInContext('safeEval(orderLinesData)', sandbox, { timeout: 2000 })
  ```
- **High-Level Abuse Scenario:** An attacker with B2B API access could craft `orderLinesData` to escape the sandbox and execute arbitrary code on the server, potentially gaining shell access.
- **Preconditions:** Authenticated user with access to `/b2b/v2/orders`. Challenge must be enabled.
- **Impact:** Full server compromise; arbitrary code execution; data exfiltration; lateral movement.
- **Likelihood:** High
- **Remediation:** Remove eval-based processing entirely. Parse order data using JSON schema validation. If dynamic evaluation is required, use a hardened isolated environment (e.g., WebAssembly sandbox).
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed. Node.js `vm` module is explicitly documented as not a security mechanism.

### [PT-005] XXE Injection via File Upload

- **Severity:** Critical
- **CVSS v3.1:** 9.1 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-611 (Improper Restriction of XML External Entity Reference)
- **OWASP Category:** A05:2021 – Security Misconfiguration
- **Affected Files/Locations:** `routes/fileUpload.ts`, lines 80-83
- **Description:** The XML file upload handler parses XML with `noent: true`, which enables XML External Entity expansion, allowing file disclosure and SSRF.
- **Technical Details:** The `libxmljs2.parseXml` is called with `{ noblanks: true, noent: true, nocdata: true }`. The `noent: true` flag causes external entity expansion.
- **Evidence from Code:**
  ```typescript
  // routes/fileUpload.ts:83
  const xmlDoc = vm.runInContext('libxml.parseXml(data, { noblanks: true, noent: true, nocdata: true })', sandbox, { timeout: 2000 })
  ```
- **High-Level Abuse Scenario:** An attacker uploads an XML file with external entity declarations pointing to system files (e.g., `/etc/passwd`) or internal services. The parsed content is reflected in the error response.
- **Preconditions:** File upload endpoint accessible; XML file type accepted.
- **Impact:** Arbitrary file read from server filesystem; potential SSRF to internal services; denial of service via billion laughs attack.
- **Likelihood:** High
- **Remediation:** Disable external entity processing: set `noent: false` or use a safe parser configuration. Validate and sanitize XML input.
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed. The error response includes parsed XML content at line 87.

### [PT-006] NoSQL Injection in Order Tracking

- **Severity:** High
- **CVSS v3.1:** 8.6 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:L)
- **CWE:** CWE-943 (Improper Neutralization of Special Elements in Data Query Logic)
- **OWASP Category:** A03:2021 – Injection
- **Affected Files/Locations:** `routes/trackOrder.ts`, line 18
- **Description:** The order tracking endpoint uses `$where` with string interpolation, enabling NoSQL injection.
- **Technical Details:** The MongoDB `$where` clause evaluates JavaScript with user-controlled input: `this.orderId === '${id}'`. The input is only truncated to 60 characters, which is sufficient for injection.
- **Evidence from Code:**
  ```typescript
  // routes/trackOrder.ts:18
  db.ordersCollection.find({ $where: `this.orderId === '${id}'` })
  ```
- **High-Level Abuse Scenario:** An attacker could inject JavaScript into the `id` parameter to bypass the query logic and retrieve all orders, e.g., `' || true || '`.
- **Preconditions:** None — unauthenticated endpoint.
- **Impact:** Unauthorized access to all order data; information disclosure.
- **Likelihood:** High
- **Remediation:** Use standard query operators instead of `$where`. Use `{ orderId: id }` as the query filter.
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed.

### [PT-007] Server-Side Request Forgery (SSRF) via Profile Image URL

- **Severity:** High
- **CVSS v3.1:** 8.6 (AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:L/A:N)
- **CWE:** CWE-918 (Server-Side Request Forgery)
- **OWASP Category:** A10:2021 – Server-Side Request Forgery
- **Affected Files/Locations:** `routes/profileImageUrlUpload.ts`, line 24
- **Description:** The profile image URL upload endpoint fetches an arbitrary URL provided by the user using `fetch()` without URL validation or allowlisting.
- **Technical Details:** The user-supplied `imageUrl` is directly passed to `fetch(url)`. There is no validation of the URL scheme, host, or port. Internal network addresses, cloud metadata endpoints, and local files could be targeted.
- **Evidence from Code:**
  ```typescript
  // routes/profileImageUrlUpload.ts:24
  const response = await fetch(url)
  ```
- **High-Level Abuse Scenario:** An attacker could provide URLs pointing to internal services (e.g., `http://169.254.169.254/latest/meta-data/` on AWS) to exfiltrate cloud credentials or scan internal networks.
- **Preconditions:** Authenticated user.
- **Impact:** Internal network scanning; cloud metadata credential theft; access to internal services.
- **Likelihood:** High
- **Remediation:** Implement URL allowlisting. Block private IP ranges, loopback, and link-local addresses. Validate URL scheme (only allow https).
- **Remediation Priority:** High (P1)
- **Validation Notes:** Confirmed. The code also sets `req.app.locals.abused_ssrf_bug` on a specific pattern match.

### [PT-008] Local File Read via Data Erasure (Server-Side Template Injection / LFR)

- **Severity:** High
- **CVSS v3.1:** 8.1 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N)
- **CWE:** CWE-94 (Improper Control of Generation of Code)
- **OWASP Category:** A03:2021 – Injection
- **Affected Files/Locations:** `routes/dataErasure.ts`, lines 68-80
- **Description:** The data erasure POST handler allows a user-controlled `layout` parameter to be passed to the Handlebars `res.render()` function. This enables local file inclusion by specifying an arbitrary layout file path.
- **Technical Details:** The `req.body.layout` value is resolved to an absolute path and used as the Handlebars layout. While there is a blocklist check for `ftp`, `ctf.key`, and `encryptionkeys`, other files on the filesystem can still be read.
- **Evidence from Code:**
  ```typescript
  // routes/dataErasure.ts:69
  const filePath: string = path.resolve(req.body.layout).toLowerCase()
  const isForbiddenFile: boolean = (filePath.includes('ftp') || filePath.includes('ctf.key') || filePath.includes('encryptionkeys'))
  if (!isForbiddenFile) {
    res.render('dataErasureResult', { ...req.body }, ...)
  }
  ```
- **High-Level Abuse Scenario:** An attacker could specify `layout` as a path to sensitive files (e.g., `/etc/passwd`, source code files) and have partial content returned in the response.
- **Preconditions:** Authenticated user with an active session.
- **Impact:** Arbitrary file read (with some content truncation); information disclosure; potential for further exploitation.
- **Likelihood:** Medium
- **Remediation:** Remove the ability to specify layout files from user input. Use a hardcoded layout. If dynamic layouts are needed, use a strict allowlist.
- **Remediation Priority:** High (P1)
- **Validation Notes:** Confirmed. The response is truncated to 100 characters.

### [PT-009] Open Redirect

- **Severity:** Medium
- **CVSS v3.1:** 6.1 (AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N)
- **CWE:** CWE-601 (URL Redirection to Untrusted Site)
- **OWASP Category:** A01:2021 – Broken Access Control
- **Affected Files/Locations:** `routes/redirect.ts`, `lib/insecurity.ts` lines 135-141
- **Description:** The redirect allowlist check uses `url.includes(allowedUrl)` instead of a strict prefix match, allowing bypass by including an allowed URL as a substring of a malicious URL.
- **Technical Details:** The `isRedirectAllowed` function checks if any allowlisted URL is a *substring* of the target URL. An attacker can craft URLs like `https://evil.com?https://github.com/juice-shop/juice-shop` to pass the check.
- **Evidence from Code:**
  ```typescript
  // lib/insecurity.ts:138
  allowed = allowed || url.includes(allowedUrl)
  ```
- **High-Level Abuse Scenario:** An attacker crafts a link to `/redirect?to=https://evil.com?https://github.com/juice-shop/juice-shop` which passes validation and redirects the victim to a phishing site.
- **Preconditions:** Victim clicks a crafted link.
- **Impact:** Phishing; credential theft; reputation damage.
- **Likelihood:** Medium
- **Remediation:** Use strict URL comparison: check that the target URL starts with an allowed URL prefix using `url.startsWith(allowedUrl)`.
- **Remediation Priority:** Medium (P2)
- **Validation Notes:** Confirmed.

### [PT-010] Weak Password Hashing (MD5, No Salt)

- **Severity:** High
- **CVSS v3.1:** 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)
- **CWE:** CWE-328 (Use of Weak Hash)
- **OWASP Category:** A02:2021 – Cryptographic Failures
- **Affected Files/Locations:** `lib/insecurity.ts`, line 43
- **Description:** Passwords are hashed using MD5 without any salt. MD5 is cryptographically broken and highly vulnerable to rainbow table and brute-force attacks.
- **Technical Details:** `crypto.createHash('md5').update(data).digest('hex')` is used for all password hashing.
- **Evidence from Code:**
  ```typescript
  // lib/insecurity.ts:43
  export const hash = (data: string) => crypto.createHash('md5').update(data).digest('hex')
  ```
- **High-Level Abuse Scenario:** If password hashes are obtained (via SQL injection, database breach, or data export), they can be reversed almost instantly using rainbow tables or GPU-accelerated cracking.
- **Preconditions:** Access to password hashes.
- **Impact:** Mass credential compromise.
- **Likelihood:** Very High (when combined with SQL injection)
- **Remediation:** Use bcrypt, scrypt, or Argon2id with appropriate work factors and automatic salting.
- **Remediation Priority:** Immediate (P0)
- **Validation Notes:** Confirmed.

### [PT-011] Broken Access Control on Baskets (IDOR)

- **Severity:** High
- **CVSS v3.1:** 7.5 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:L/A:N)
- **CWE:** CWE-639 (Authorization Bypass Through User-Controlled Key)
- **OWASP Category:** A01:2021 – Broken Access Control
- **Affected Files/Locations:** `routes/basket.ts`
- **Description:** The basket retrieval endpoint uses the basket ID from the URL parameter without verifying it belongs to the authenticated user. The check only *detects* the challenge condition but does not *prevent* access.
- **Technical Details:** The route `/rest/basket/:id` retrieves the basket by the URL-supplied `:id`. The `challengeUtils.solveIf` call checks if the user's bid mismatches the requested ID, but does **not** deny access.
- **Evidence from Code:**
  ```typescript
  // routes/basket.ts:21-23
  challengeUtils.solveIf(challenges.basketAccessChallenge, () => {
    const user = security.authenticatedUsers.from(req)
    return user && id && id !== 'undefined' && id !== 'null' && id !== 'NaN' && user.bid && user?.bid != parseInt(id, 10)
  })
  ```
- **High-Level Abuse Scenario:** An authenticated user changes the basket ID in the API request to access other users' baskets.
- **Preconditions:** Authenticated user.
- **Impact:** Information disclosure of other users' cart contents.
- **Likelihood:** High
- **Remediation:** Enforce server-side authorization: verify the basket belongs to the requesting user before returning data.
- **Remediation Priority:** High (P1)
- **Validation Notes:** Confirmed.

### [PT-012] Broken Access Control on Product Reviews

- **Severity:** Medium

## 6. Attack Path Observations

### Attack Chain 1: Unauthenticated Full Compromise
1. **SQL Injection** (PT-001/PT-002) → Extract all user credentials (emails + MD5 hashes)
2. **Weak Password Hashing** (PT-010) → Crack MD5 hashes via rainbow tables
3. **Login as Admin** → Full administrative access
4. **Alternate path:** Use hardcoded private key (PT-003) to forge admin JWT directly

### Attack Chain 2: SSRF to Internal Network Pivot
1. **Authenticate** as any user (via SQL injection or registration)
2. **SSRF** (PT-007) → Scan internal network, access cloud metadata endpoints
3. **Exfiltrate cloud credentials** → Pivot to infrastructure

### Attack Chain 3: XSS → Account Takeover
1. **Stored XSS** (PT-014) → Steal admin JWT token from cookie
2. **Change Password without current password** (PT-023) → Take over admin account
3. **Mass Assignment** (PT-026) can also achieve admin access directly

### Attack Chain 4: File-Based Exploitation
1. **Directory Listing** (PT-022) → Discover sensitive files
2. **Path Traversal** (PT-016) → Access backup files with credentials
3. **Zip Slip** (PT-017) → Overwrite application files for persistence
4. **XXE** (PT-005) → Read arbitrary files from filesystem

### Attack Chain 5: Business Logic Abuse
1. **Coupon Forgery** (PT-028) → Generate high-discount coupons
2. **Wallet Manipulation** (PT-029) → Add arbitrary funds

## 7. Positive Security Controls Observed

Despite the intentionally vulnerable nature, the following positive security controls are present:

1. **Helmet.js Integration** — `helmet.noSniff()` and `helmet.frameguard()` are enabled (`server.ts:185-186`), providing some HTTP header security.
2. **X-Powered-By Disabled** — `app.disable('x-powered-by')` reduces information leakage (`server.ts:188`).
3. **Feature Policy** — Payment feature is restricted to same-origin (`server.ts:189-192`).
4. **Rate Limiting** — Rate limiting is applied to password reset and 2FA endpoints (though bypassable).
5. **File Upload Size Limits** — Multer is configured with `limits: { fileSize: 200000 }` (`server.ts:681`).
6. **MIME Type Validation** — Profile image upload validates MIME type via `file-type` library (`routes/profileImageFileUpload.ts:24-33`).
7. **Duplicate Slash Normalization** — URL path normalization prevents filter bypass via double slashes (`server.ts:202-205`).
8. **Forward Slash Block in File Serving** — File serving routes block forward slashes in filenames, preventing basic directory traversal.
9. **2FA Support** — TOTP-based 2FA is available for user accounts.
10. **Paranoid Delete** — User model uses `paranoid: true` for soft deletion (`models/user.ts:125`).
11. **Distroless Docker Image** — Production Dockerfile uses `gcr.io/distroless/nodejs24-debian13` as the base image, minimizing attack surface.
12. **Non-Root Container** — Dockerfile specifies `USER 65532` for running the application.
13. **Secure Sanitization** — `sanitizeSecure` function provides recursive HTML sanitization when challenges are not active.
14. **Access Logging** — Morgan logging with rotating log files for audit trail.
15. **Compression** — Response compression is enabled for performance.
